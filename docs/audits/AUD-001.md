# AUD-001 — PoB item-set import contract

## Status

supported

Evidence was inspected on 2026-08-01. The current profile is pinned to Path of
Building Community release 2.66.2 at commit
`b23da8f841e4b0bc167b0b4401ea002d7d45f807` and checked against development
commit `ef4c5848fad33190f730cebaedff4b5831d0c88d`. Historical compatibility
evidence is pinned separately below.

## Question

Can Golden Glory Lab reliably accept a Path of Building share code or raw XML,
enumerate all item sets, preserve their names, identifiers, complete item text,
slot assignments, weapon-set state, and relevant child sockets, and let users
explicitly map one set to the player and another to the Mercenary without using
item-set order as ownership?

## Product impact

This audit defines the evidence boundary for a later parser PROOF. It supports
PoB share-code and XML intake, player-loadout extraction, user-designated
Mercenary equipment extraction, item-set comparison, recognition reporting,
and reviewable reimport. PoB remains an import container and supporting source;
it is not an authority for permanent Mercenary calculations.

## Scope

Included are the share-code envelope, decompressed XML, the item pool, item
sets, active and alternate weapon-set state, equipment and child-slot
references, passive-tree jewel references, identifier behavior, legacy item-set
representations, and source material available for later reimport comparison.

Excluded are application or parser implementation, desktop-framework choice,
merge-policy design, private builds, and all Flame Link, Golden Glory, Light
Radius, Enmity's Embrace, Resistance, and critical-strike mechanics.

## Source plan

The audit inspected, in order:

1. the tagged 2.66.2 Path of Building Community source and the current `dev`
   source at exact commits;
2. committed build fixtures and import/reimport tests at the current `dev`
   commit;
3. the source history that predates and introduces item sets, including its
   changelog;
4. the companion SimpleGraphic host implementation that provides PoB's
   `Deflate` and `Inflate` functions.

No formal, versioned XML schema was found in the inspected repositories. The
contract therefore distinguishes current implementation behavior, explicit
legacy handling, incidental fixture shapes, and proposed Golden Glory Lab
behavior.

## Evidence

### Evidence-address convention

Unless another commit is stated, paths beginning with `src/` or `runtime/`
refer to `PathOfBuildingCommunity/PathOfBuilding` at
`ef4c5848fad33190f730cebaedff4b5831d0c88d`. The release comparison uses the
same paths at `b23da8f841e4b0bc167b0b4401ea002d7d45f807`. Exact repository URLs,
commits, versions, supported claims, and limitations are recorded under the
source IDs above.

### Encoded intake

- `src/Classes/ImportTab.lua :: self.controls.generateCode` callback serializes the build XML,
  passes it to host `Deflate`, applies standard Base64, and substitutes `-`
  for `+` and `_` for `/`. The local `importCodeHandle` callback reverses
  those two substitutions, decodes Base64, and calls host `Inflate`.
- `runtime/lua/base64.lua :: encode/decode` uses the standard Base64
  alphabet and padding. Its decoder removes characters outside its accepted
  alphabet; that permissive current behavior is not evidence that a new
  importer should silently discard input.
- `PathOfBuildingCommunity/PathOfBuilding-SimpleGraphic/ui_api.cpp ::
  l_Deflate/l_Inflate` at
  `3b1a3468223d0ebd4042d6ce76fc6144718ef79b` calls zlib's `deflateInit`
  and `inflateInit`. The share envelope is therefore URL-safe-substituted
  Base64 of a zlib-wrapped DEFLATE stream, not raw DEFLATE. The current host
  contains 128 MiB input and output checks, but `l_Inflate`'s oversized-input
  branch pushes an error and then falls through because it does not return.
  Its initial output allocation is not capped by the nominal output threshold,
  and its later growth check can grow once beyond that threshold. These checks
  are implementation evidence and known limitations, not safety controls or
  permanent format promises for Golden Glory Lab.

### XML document and identifier behavior

- `src/Modules/Build.lua :: buildMode:LoadDB` requires the first XML
  element to be `PathOfBuilding`, loads `Build` first, and dispatches known
  top-level sections including `Items`, `Tree`, and `Skills`.
  `buildMode:SaveDB` writes the same root and registered sections. Top-level
  elements without a registered loader are not retained by PoB's current model.
- `src/Classes/ItemsTab.lua :: ItemsTabClass:Load/Save` treats repeated
  `Item` elements as a document-level item pool and nested `ItemSet`
  elements as sets whose `Slot/@itemId` values refer to that pool. It
  retains an explicit item-set order list for display/save order, while
  active-set and other semantic references use item-set IDs.
- `src/Classes/ItemsTab.lua :: ItemsTabClass:NewItemSet/AddItem` allocates
  the lowest unused positive integer when an ID is not supplied. Deletion and
  recreation can therefore reuse an ID. `ItemSetListControl.lua` permits
  rename, copy, delete, and reorder operations; copy deliberately reuses item
  pool references. Neither numeric IDs, titles, nor order are established as
  cross-document identities.
- `src/Classes/SkillsTab.lua :: LoadSkill/Save` serializes
  `Gem/@skillMinionItemSet` and `Gem/@skillMinionItemSetCalcs` as
  numeric item-set references. On current `dev`,
  `src/Classes/ImportTab.lua ::
  GetOrCreateGuardianItemSet/AssignGuardianItemSet` explicitly locates or
  creates a set named `Animate Guardian` and assigns its ID. This is evidence
  for explicit ID-based cross-references, not evidence that any PoB set belongs
  to a permanent Mercenary.
- `src/Classes/Item.lua :: ItemClass:ParseRaw/BuildRaw/BuildAndParseRaw`
  parses an item's text and recognizes a `Unique ID:` line when present. The
  current saver calls `BuildAndParseRaw` before serialization, so a PoB save
  may rebuild or normalize item text. A downstream importer cannot recover
  byte-exact intake text unless it preserves that text itself.
- `src/Classes/ImportTab.lua :: ImportItem` stores the PoE API item ID as
  the parsed item's `uniqueID`. Its current reimport path matches that value,
  keeps the existing local numeric `Item/@id`, and overwrites the item;
  otherwise `AddItem` allocates a local ID. This behavior does not establish
  that every serialized item has a `Unique ID:` line or that the value is a
  universal, permanent identity.

### Historical representations

- At Path of Building 1.4.36 commit
  `69d4e4d4e4cfb82ccca0ebf609d6673e347a98dc`,
  `Classes/ItemsTab.lua :: Load/Save` stores selected equipment as top-level
  `/Items/Slot` elements and alternate-weapon state as
  `/Items/@useSecondWeaponSet`; there are no `ItemSet` elements.
- At 1.4.37 commit `9f981583f7c721917124d604cddf0e8102e62714`,
  the same file introduces `ItemSet/@id`, `@title`, per-set
  `@useSecondWeaponSet`, and nested `Slot` elements. That release still
  writes the active selection as top-level slots as well as writing nested item
  sets, producing a transitional dual representation. Its `changelog.txt`
  describes item sets as switchable gear configurations and minion selection
  by item set.
- Current `ItemsTabClass:Load` still reads top-level `/Items/Slot` as an
  obsolete legacy representation. If no nested set is present, it creates set
  ID `1`; the current saver writes nested sets instead.
- The five committed `spec/TestBuilds/3.13/*.xml` fixtures use one unnamed
  set and retain both legacy top-level slots and nested set slots. They
  demonstrate examples, not a complete grammar: they do not cover named
  multiple sets, active alternate weapons, non-empty Abyssal equipment slots,
  malformed references, or current-version breadth.

## Conflicts and gaps

- No formal PoB XML schema, declared serialization-format version, or root-level
  application version was identified. The inspected source is the executable
  contract for the pinned commits, not a promise about future input.
- `Build/@targetVersion` looks version-like but selects game data; treating it
  as the PoB application version would be incorrect. For raw XML and share
  codes, the producing application version is normally unknown unless supplied
  out of band.
- Current PoB drops unknown top-level sections, unknown item-set slot names, and
  item text it cannot resolve to a known base from its in-memory model. That
  behavior conflicts with Golden Glory Lab's preservation requirement and must
  not be copied into the neutral loader.
- The current Base64 decoder strips invalid characters. Whether such input was
  merely line-wrapped or corrupted is ambiguous; a future adapter must report
  normalization rather than silently changing evidence.
- PoB's current saver can normalize item text. The original raw XML or decoded
  XML is therefore the only byte-preserving source envelope available to Golden
  Glory Lab.
- The committed fixtures are old and narrow. The current code and history
  establish structures that those fixtures do not exercise, but only a parser
  PROOF with purpose-built fixtures will establish Golden Glory Lab behavior.
- Neither source nor fixtures establish a player/Mercenary ownership field.
  The current Animate Guardian helper is for a different entity and cannot fill
  that gap.
- No source establishes item IDs, item-set IDs, titles, slot occurrence order,
  or `Unique ID:` values as universally stable across independently generated
  documents.

## Analysis

### Reliability boundary

The evidence supports a versioned loader profile, not unrestricted acceptance
of all past and future PoB documents. Within the pinned current profile, a
separate share-code adapter can recover XML and a neutral XML loader can
enumerate all pool items, all nested item sets, explicit references, alternate
weapons, named Abyssal child slots, and passive-tree jewels without running
PoB. The same loader can recognize two historical profiles:

1. legacy top-level slots without nested item sets, represented in the neutral
   output as one explicitly marked synthesized set; and
2. transitional documents containing both top-level slots and nested item
   sets, where nested sets are enumerated and the legacy representation is
   retained as source material rather than counted as another set.

Unknown versions, elements, attributes, slot names, duplicate IDs, and broken
references remain parse results with warnings; they are not grounds to discard
the rest of a readable document. This is proposed Golden Glory Lab behavior,
not a claim about current PoB behavior.

Parsing untrusted input also requires bounded Base64, decompression, and XML
sizes and nesting; rejection of DTDs and external entities; no network access;
and stable errors for truncated or over-limit material. Exact limits belong to
the PROOF, not this format audit.

### Ownership-mapping conclusion

The supported Golden Glory Lab rule is:

1. enumerate every item set in source order for faithful display;
2. show each set's original ID, title (including missing or empty), whether its
   ID matches the retained active-set reference, and alternate-weapon state;
3. require the user to choose the player set by an import-local occurrence
   identity that remains unique even when raw item-set IDs are duplicated;
4. allow the user to choose a different Mercenary set occurrence or choose
   "no Mercenary item set" for later manual equipment entry;
5. optionally suggest candidates from names, while labeling the suggestion and
   requiring confirmation; and
6. store the confirmed ownership mapping outside the imported PoB facts.

Item-set order, the active set, a generic or missing name, a minion
cross-reference, and the presence of any unique item are not ownership
evidence. In particular, a set containing Enmity's Embrace must never be
automatically assigned to the Mercenary.

### Proposed neutral intermediate representation

The following is a language-neutral data contract, not an implementation or a
JSON Schema selection:

| Object | Required neutral fields |
| --- | --- |
| envelope | `irVersion`; input kind (`raw-xml` or `share-code`); exact original input; content hashes with algorithm and exact byte domain; exact decoded XML when applicable; codec steps and reported normalization; observed byte/character counts; parser evidence source IDs and commits |
| source metadata | externally supplied PoB version when available; otherwise `null`; `Build/@targetVersion` as a separately named game target; other observed version-like values without reinterpretation |
| document | root name; ordered top-level node inventory; unknown attributes/elements and retained raw fragments; document-level warnings |
| item | source occurrence index; raw ID lexeme; parsed numeric ID when valid; every original attribute; the complete XML character value assembled from text and CDATA children; ordered child nodes such as `ModRange`; a raw inner-XML span or lexeme when the chosen parser can supply one; optional recognized fields clearly separated from source material; item warnings |
| item set | source occurrence index; raw and parsed ID; title with missing/empty distinction; raw and parsed `useSecondWeaponSet`; ordered slot assignments; `SocketIdURL` records; unknown children; set warnings; legacy/synthesized provenance when applicable |
| assignment | occurrence index; original slot name; raw and parsed item reference; `active` and `itemPbURL` lexemes; reference-resolution status; optional derived parent-slot hint with the source name retained |
| selection | raw and parsed active item-set reference; resolution status; no inferred player or Mercenary owner |
| other references | passive-spec jewel assignments and item-set cross-references, each with its XML path, raw lexemes, source order, and resolution status |
| report | ordered entries in the recognition categories below, with stable locations and codes |

Arrays preserve source occurrence order, while deterministic output fixes field
ordering, normalization rules for derived hashes, and warning ordering. Source
order is fidelity data only. Equivalent raw-XML and share-code fixtures should
produce the same semantic document portion while keeping different envelope
metadata.

The exact original or decoded XML is the byte-fidelity authority. XML parsers
normally normalize line endings and entity references before exposing a text
value, so the per-item field promises the complete XML character value, not a
byte-exact reconstruction of the item's inner XML. A PROOF may expose a
byte-exact per-item source span only if its parser reports trustworthy offsets;
it must not recreate and label normalized text as the original lexeme.

No calculated Flame Link, Resistance, critical-strike, item-range, or
Mercenary value belongs in this representation. Observed item text remains
valid even when a modifier lies outside a natural catalog range.

### Recognition-report boundary

| Category | Meaning | Original material retained |
| --- | --- | --- |
| recognized | Structure or value parsed under a pinned profile. | Raw lexeme or text, original XML path and occurrence, attributes, and any raw fragment needed to audit the parsed value. |
| ignored as irrelevant | Readable material intentionally outside the neutral equipment scope. | Raw document/subtree or recoverable fragment, path, and an explicit reason; never silent deletion. |
| unrecognized | Well-formed structure has no rule in the pinned profile. | Entire ordered subtree, attributes, text, path, and a warning code. |
| ambiguous | More than one interpretation or reference target remains possible. | All candidate IDs/occurrences, the unmodified source, and why no choice was made. |
| manually required | A needed player/Mercenary choice or value is not present in PoB. | Missing-value marker, relevant context and candidates, and any later user-supplied value as a separate fact. |
| malformed | The envelope, XML, lexeme, ID, or reference violates the recognized shape. | For a readable XML tree, the offending raw lexeme or subtree, exact location, stable error, and safely parsed siblings. For a fatal envelope, decompression, or XML-well-formedness failure, the complete original input, failing stage, and byte/line/column location when available; no invented partial tree or numeric coercion. |

Recovery is stage-specific. A well-formed XML document with a nonnumeric ID or
broken reference can retain the occurrence and continue with siblings. Invalid
Base64, a failed zlib stream, or ill-formed XML may prevent any trustworthy
tree from existing; those cases terminate that stage with the whole source
envelope retained and do not require parser-error recovery or a partial IR.

### Reimport evidence boundary

Within one imported document, numeric `Item/@id` values can join the item pool
to item-set slots and passive sockets. Numeric `ItemSet/@id` values can join
sets to `Items/@activeItemSet` and minion cross-references. Reusing one item ID
across several sets is normal. Duplicate item or item-set ID declarations,
multiple conflicting assignments for one set slot, and missing targets must be
preserved as occurrences and reported rather than resolved by last-write wins.

Across imports, local item and item-set IDs are only candidates: current PoB
allocates the lowest unused integer and permits rename, reorder, copy, and
deletion. A `Unique ID:` line is a stronger candidate when present because
PoB's API reimport uses it, but its availability and lifetime are not
established for all input. Titles are mutable and non-unique. Slot plus exact
item text/hash, canonicalized text/hash, base/name, and modifier text can supply
reviewable fallback evidence, but this audit does not choose a merge algorithm.

A future diff therefore needs the original share code or XML, exact decoded
XML, envelope and document hashes, raw and parsed IDs, every original item text
block, attributes, source occurrence order, slot references, titles,
active/weapon-set state, resolution status, and prior warnings. User-confirmed
ownership and manual overrides are separate application facts and must not be
overwritten merely because another PoB was imported.

## Conclusion

**Supported, within a pinned profile:** Golden Glory Lab can later implement a
share-code adapter and neutral XML loader that enumerate and preserve the
audited PoB loadout structures. The user must explicitly map import-local set
occurrences to the player and optional permanent Mercenary; a raw item-set ID
is sufficient for that choice only when it resolves uniquely. Item-set order
has no ownership meaning.

The conclusion is not `confirmed` because PoB provides no embedded application
format version or formal stable schema, current PoB itself discards or
normalizes some input, committed fixtures do not cover the whole scope, and the
proposed preservation behavior has not yet been proven in Golden Glory Lab.

## Non-conclusions

This audit does not establish:

- arbitrary future or malformed PoB compatibility;
- cross-document stability of item IDs, item-set IDs, titles, occurrence order,
  or `Unique ID:` values;
- a complete reimport matching or merge policy;
- the meaning or correctness of item modifiers, natural ranges, item
  availability, or any game-mechanics calculation;
- permanent Mercenary passive stats or PoB authority over permanent Mercenary
  calculations;
- ownership from Animate Guardian, minion, active-set, name, item, or order
  metadata;
- completeness of PoB's slot vocabulary for future releases;
- a parser implementation, application framework, UI, or combined build score.

## Dataset impact

Seven PoB source records are added to the source registry. No curated or
generated Path of Exile mechanics data, application schema, parser code, or
upstream PoB snapshot is added.
